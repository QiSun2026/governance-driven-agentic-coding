Result path

Three layers that must not collapse

An evaluation can support or block a decision. It cannot turn technical evidence into acceptance, release authority, or a compliance claim.

One path, three different questions

Technical eval

Does the frozen claim pass its declared procedure and evidence rule? Result: pass, fail, insufficient_evidence, or not_evaluated.

Harness Gate

Are all blocking checks complete, passed, and free of unresolved material findings? Result: blocked or ready.

Owner disposition

What should happen for this purpose and version? The accountable Owner records accept, accept_with_conditions, rework, pause, or stop.

Conditions for each technical evaluation result state
StateUse it only when
passThe declared procedure is valid, every required evidence item is valid and bound to the candidate, and the frozen pass rule is met.
failThe procedure and required evidence are valid and bound, but the frozen pass rule is not met.
insufficient_evidenceMissing, invalid, stale, unbound, or unadjudicated contradictory evidence prevents a decision under the pass rule.
not_evaluatedThe declared evaluation did not run.

A valid result that disproves the pass rule is a failure. Conflicting records that have not been adjudicated are insufficient evidence; the evaluator may not choose the favorable record.

Authority boundary

Owner acceptance is not an eval claim and receives no pass score. A technically complete package is ready for a decision, not already accepted.

Pre-build plan

The Eval Plan is frozen before implementation

The plan says what will be tested and how the future candidate will be selected. It does not invent a candidate_ref before that candidate exists.

Class / grader

Eval class and grader type answer different questions

eval_class describes what is being tested. grader.type describes how the evidence is judged. Model and human are grader types, not evaluation classes.

Evaluation classes

Evaluation classes and failure consequences
ClassQuestionTypical consequence
ContractAre the outcome, non-goals, authority, budget, stops, and material claims testable and frozen?Block before execution.
CapabilityDoes the claimed new behavior occur on the declared path and environment?Fail the claim or mark evidence insufficient.
RegressionDoes previously accepted behavior still work on the new candidate?Block the candidate when required behavior breaks.
AdversarialCan abnormal input, permission misuse, hidden paths, unsafe fallback, or evidence substitution defeat the claim?Preserve findings and block unresolved material cases.
SecurityDo applicable threat and control checks support the declared security claim?Escalate specialist findings and block missing required evidence.
PrivacyDoes data handling stay within the declared collection, use, retention, and disclosure boundary?Block or require accountable specialist review.
GovernanceWere authority, separation, evidence binding, stop rules, and handoff controls actually followed?Block a package with a broken control path.

Grader types

Deterministic code
Use executable checks when they directly answer the claim. Preserve the environment, fixture, output, and failure record.
Deterministic rule
Use an explicit rule when the evidence can be judged mechanically without model interpretation.
Model grader
Use only when the claim cannot be reduced reliably. Freeze its configuration and rubric, retain a calibration reference for the declared claim distribution, and never use it as the sole blocking grader for a material claim.
Qualified human
Use for ambiguous material judgment or specialist interpretation. Record the review configuration and a qualification reference; human grading still remains separate from Owner acceptance.
Not a grader

The Owner is not a fallback for missing technical evidence. Owner authority resolves reserved decisions after the evidence package is assembled.

Record and gate

Evidence remains attached to the claim and candidate

Every record identifies what it supports, where it came from, how it was produced, and what it cannot establish. Evidence from another version or environment is not silently reused.

Claim

The exact claim supported or contradicted.

Candidate Binding

The immutable artifact, digest, source revision, attempt, and relevant environment.

Producer identity

The evidence type, role, principal, context, and required separation.

Procedure

Inputs, fixtures, steps, tools, and configuration.

Raw result

The output or a stable reference to the retained record.

Integrity

Digest, provenance, or other integrity information when available.

Observed state

Pass, fail, measured value, or a clear insufficient-evidence state.

Limits

Known limitations, contradictions, and unresolved unknowns.

The current validator aggregates these checks from a supplied Gate Record into one blocked or ready state. Runtime identity, write-scope enforcement, and evidence production still belong to the Agent platform, repository, CI, or eval system named by the Contract.

Identity and risk

Select by rule, bind after building

The pre-build plan identifies the subject by rule. Evaluation begins only after that rule resolves to one exact candidate and the binding is recorded.

  1. 01Freeze the selection rule. Name the component, interface, behavior, baseline, or evidence record before implementation.
  2. 02Create the Candidate Binding. Resolve the rule to an immutable snapshot and record the Eval Plan version.
  3. 03Invalidate honestly. If the candidate, contract, plan, fixture, grader procedure, or relevant environment changes, preserve the original result and mark affected evidence invalid.
  4. 04Version and rerun. Create a new binding or plan version, then rerun every affected required eval. Do not continue the old review against a changed object.

Bounded repetition

Retries, reruns, and trials are different events

Naming the event correctly prevents a changed candidate, an infrastructure rerun, and a repeated reliability sample from being merged into one convenient pass.

Builder retry
Changes implementation, configuration, or another material input. It creates a new attempt and Candidate Binding and consumes the Outcome Contract budget.
Evaluator rerun
Repeats the same procedure on the same candidate after a declared execution or infrastructure error. It consumes the eval's max_evaluator_reruns and the Contract's total rerun budget.
Repeated trial
Runs one predeclared sample inside a reliability question. The plan fixes the trial policy and value of k before results are visible.

Single

One declared trial. Do not infer a repeated-trial percentage from it.

pass@k

Use stored policy pass-at-k only when at least one success across k genuine trials answers the claim.

pass^k

Use stored policy pass-power-k only when all k trials must succeed.

Repeated-trial pass selection is prohibited for blocking regression, adversarial, security, privacy, and governance checks. Every declared trial counts and remains in the record.

Retention is declared before execution

Keep the applicable Outcome Contract and Eval Plan versions, subject-selection rule, Candidate Bindings, stable evidence references, eval results, grader configuration, failed attempts, gate state, and Owner disposition through closeout.

The plan always retains stable evidence references, digests, and all attempts. Raw sensitive inputs or outputs may be omitted or redacted under a declared basis and retention period, but evidence supporting a maintained claim must remain traceable for as long as that claim is maintained.

A later pass does not delete an earlier failure, a known limitation, or the cost and reason for a material attempt. Repeated identical blockers stop the work.

Worked rule

A dry-run claim is only as strong as its declared boundary

A cleanup command must preview the exact change set without initiating a filesystem write through the inventoried write-capable APIs inside the declared candidate-process and fixture boundary.

Frozen claims

What must be established before the task can be decision-ready.

Bounded no-write claim

Inside the declared boundary, dry-run calls none of the candidate's inventoried write-capable APIs. The inventory must cover temporary-file, rename, deletion, and metadata paths when present.

Accurate preview

The preview matches every path that equivalent normal execution would create, change, or remove.

Regression safety

Existing behavior without the dry-run flag continues to pass the protected baseline.

Failure-path safety

Interruption, denied permissions, temporary-file paths, hidden paths, and nested boundaries do not trigger an inventoried write API or produce a misleading preview.

Suitable graders

Deterministic evidence answers the claims directly.

Instrumented write trace

Record every application-initiated write in the declared process tree and filesystem boundary. Claims one and four pass only when the trace records zero write calls.

Preview comparison

Compare the dry-run change set with normal execution on an equivalent clean fixture.

Regression suite

Run the accepted command suite without the dry-run flag on the bound candidate.

Adversarial cases

Exercise interruption, permissions, temporary files, hidden paths, and scope boundaries in separated review context.

Evidence rule

Primary evidence and supporting evidence are not interchangeable.

Primary evidence

The API inventory must have no uncovered write path and the trace must record zero calls. A model grader adds no value when instrumentation answers the claim.

Supporting evidence

A before-and-after filesystem snapshot may corroborate the result, but cannot establish the claim because a temporary write could be removed before the final snapshot.

Blocking consequence

Any recorded write, missing trace, inaccurate preview, required regression failure, or unresolved material challenge keeps the Harness Gate blocked.

Report and limits

The report is a view, not a new source of truth

A final report gathers the original records for review. It does not overwrite failed attempts, repair missing evidence, or add authority that the Outcome Contract did not grant.

Versions

Outcome Contract, Eval Plan, subject-selection rule, and Candidate Binding.

Results

Every pass, fail, insufficient-evidence, and not-evaluated item with stable evidence references.

Usage

Builder attempts, evaluator reruns, repeated trials, time, token, and cost usage when declared or observable.

Findings

Verifier and Red Team findings, dispositions, limitations, contradictions, unknowns, and residual risk.

Gate state

The derived blocked or ready state.

Owner status

The separate disposition still required or already recorded for the exact purpose and version.

Reject these evaluation designs

Moving target

Tests or pass rules are changed after the result is known, or the candidate changes without invalidation.

Self-approval

The Builder grades its own material final claim or quietly expands its authority.

Happy path only

Material permission, interruption, fallback, security, privacy, or evidence-substitution failures remain untested.

Model for decoration

A model grader replaces deterministic evidence that could answer the claim directly.

Failure averaging

A required failed gate is averaged away, retried without record, or replaced with a default score.

Inflated claim

Synthetic or author-run evidence is presented as real-world effectiveness, independent validation, deployment authority, or compliance certification.

Current implementation boundary

This repository publishes the Harness and Eval specifications, three portable schemas, deterministic validators, and a digest-bound golden record chain. It does not publish a complete Agent runner, persistent evidence database, sandbox, deployment system, Owner identity service, or automatic compliance certification.
