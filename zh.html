当 Agent 做得比人看得更快

AI Agent 可以完成的工作越来越多，但一个人已经很难逐行检查所有产出。更难控制的，往往不是代码本身，而是代码周围那条决定链。

问题不只是 Agent 有没有写对代码，还包括：它获得了什么授权、实际改了什么、结果由什么证据支持、谁可以叫停，以及谁来判断这项工作是否可以接受。

如果这些答案只留在聊天记录里，任务就很难继续、复核或交接。Harness 把结果、权限、过程记录、评测和最终决定变成一条看得见的路径。

框架被设计来阻断的失控方式

  • Agent 悄悄扩大任务范围或权限。
  • Builder 看到结果后再修改测试标准。
  • 一段总结取代原始证据。
  • 同一个模型在同一上下文里给自己的结论打分。
  • 测试通过被直接写成 Owner 已经接受。
完整使用

重要、敏感或难以撤销

锁定 Contract 与 Eval Plan，使用隔离复核，保留完整 Gate Record，再由 Owner 作决定。

轻量使用

可撤销，但 Agent 有写权限

缩短 Contract，保留直接验收与权限检查、Candidate Binding 和简版 Gate Record。

不必使用

只读、琐碎、可本地撤销

沿用仓库现有 issue、测试、review 和 branch rules；不要为了框架制造仪式。

它放在现有 Git 工作流的什么位置

Issue / Contract → 纳入版本控制的 Eval Plan → commit SHA → CI / eval evidence → Gate Record → maintainer / Owner disposition

一个系统，五层控制

用一项任务走完整条链路

现在要给一个清理命令增加 --dry-run：准确预览将要发生的变化；在声明的候选进程和测试边界内，不调用候选所使用的任何已盘点写入接口。

先锁定任务边界

结果
准确预览完整改动集合，并且在声明边界内不触发候选所使用的任何已盘点写入接口。
验收
写入接口盘点没有遗漏，监测记录为零，预览准确，原有行为继续通过；执行前后的文件系统快照只作辅助证据。
明确不做
不重做 CLI，不换依赖，不做迁移，也不发布。
权限
Builder 只能修改该命令及其测试。
预算
最多两次实现尝试和一轮有边界的复核。
停止条件
出现意外写入、缺少环境、范围扩大或重要问题未解决。
  1. Owner 锁定 Outcome Contract。实现开始后，结果和证据要求不能在无人知情的情况下移动。
  2. 写代码前先锁定 Eval Plan。每项声明都写明由谁判断、必须提供什么证据、怎样算通过、最多重试几次，以及失败后怎么办。
  3. 执行内核只做必要改动。Builder 只碰已授权文件，并记录改动、尝试、失败和测试。
  4. 记录 Candidate Binding。把精确 artifact、digest、source revision 和 attempt 绑定在一起；对象改变就建立新 binding 并重跑受影响检查。
  5. Verifier 和 Red Team 分别检查不同失败路径。已盘点写入接口的直接监测是主要证据，执行前后快照只作辅助；如果存在未被监测的写入路径，结果就是证据不足。挑战测试覆盖临时文件、中断、权限错误和隐藏写入调用。
  6. Harness 校验 Gate Record。attempt、证据 digest、结果、冲突、finding 和 Gate 都绑定到同一个候选对象，不能用总分盖住问题。
  7. 最后由 Owner 决定。技术门槛通过只代表材料已经可以判断，不代表结果已经被接受或获准发布。

Eval 在动手前就开始

Eval Plan 是提前锁定的“声明与证据约定”，不是看到结果不错后再补一个分数。

声明→ 评测→ 判定器→ 证据→ 门槛→ 决定

开始执行前

结果约定检查

是否明确写清写入边界、准确预览、范围和可检查的验收标准？

失败：工作开始前阻塞
权限检查

是否只允许修改命令和测试，并写明预算、工具、重试与外部动作？

失败：停止并升级

针对候选版本

实现完整性

改动是否足够小，并通过适用的类型、lint、安全和环境检查？

失败：返工或停止
能力与回归

--dry-run 是否准确预览、在声明边界内没有触发任何已盘点写入接口，并且没有破坏原有命令？

失败：不通过或证据不足

交给 Owner 前

挑战与复核

临时文件、中断、权限错误、隐藏写入和证据缺口是否从隔离上下文被检查？

失败：重要问题未解决则阻塞
决策就绪

交接材料是否保留限制、未知、剩余风险和每项必需结果？

结果：继续阻塞，或交给 Owner

判定规则

确定性优先。如果代码或规则能够直接回答问题，就先用它们判断。

可能破坏既有行为时，回归检查必做。新增能力不能抵消旧功能失败。

对抗测试跟随实质风险。重要的是覆盖会改变决定的失败路径，不是堆测试数量。

模型评分必须保留配置与 calibration。任何 material claim 都不能只靠模型 grader 放行。

缺少证据默认不通过。它会成为 insufficient_evidence，不会被估算成及格。

Owner 接受不是 Eval。技术结果和 Harness Gate 只为决定准备材料；Owner disposition 是单独的授权行为，不是一个 grader 或质量分数。

阅读完整 Eval Rules

每项责任都有权力，也有边界

这里的角色不是职位名称。只有当一项责任带来新的证据、专业能力、实质不同的挑战，或能够改变状态的控制时，它才有存在价值。

Harness 中每项责任可以做和不能做的事情
责任可以做不能做
Owner锁定结果、权限、风险和验收；作出最终状态和外部行动决定。转移最终责任，或把失败和缺失证据改写成通过。
Orchestrator创建有边界的任务包，分配上下文和预算，执行停止规则。扩大范围、权限、预算或验收标准。
Builder修改已声明对象，并留下实现和测试证据。越界写入、削弱 Eval，或接受自己的工作。
Verifier针对精确候选版本运行已锁定的验收和回归检查。修改候选版本，或看到结果后重新定义成功。
Red Team挑战假设、滥用路径、边界情况和证据充分性。把上下文隔离说成第三方独立，或无限循环挑战。
Integrator整理通过材料、问题发现和交给 Owner 的决定包。隐藏阻塞项、合并失败材料，或替 Owner 决定。

任何责任都不能自行创造权限。每个重要状态变化，都必须能追到已声明的授权和足够证据。

靠记录传递决定，不靠回忆

摘要可以减少阅读负担，但不能取代原始结果约定、候选版本、测试、问题发现或 Owner 决定。

  1. Outcome Contract锁定可验证的写入边界、准确预览、权限、预算和停止规则
  2. Eval Plan把四项 dry-run 声明绑定到判定方式和必需证据
  3. 尝试记录保存实际动作、失败、资源使用和未解决问题
  4. Candidate Binding精确 artifact、digest、source revision 和 attempt
  5. 证据记录用 stable reference 和 digest 绑定写入监测、预览、回归及挑战结果
  6. Gate Record保留所有结果、冲突、finding，以及 blocked / ready 状态
  7. Owner 决定记录条件、剩余风险和下一状态
  8. 收尾记录保留成果、不能声称的内容和学习候选

Owner 视图

当前状态、重要变化、风险、阻塞和需要决定的事项。

学习视图

发生了什么失败、如何修正、建议增加什么预防检查，以及重测还需要哪些证据。

公开视图

只呈现已经被接受记录支持的事实、例子和限制。

受治理的系统必须知道何时停下

停止本身可以是一个有效的受控结果。因为已经花了时间就继续，不是。

遇到以下情况，规则要求工作继续保持 blocked

  • 缺少必要授权、输入或验收标准；
  • 准备执行的动作超出已声明范围；
  • 评测期间候选版本或 Eval Plan 发生改变；
  • 时间、token、尝试次数或 Agent 深度预算已经用完；
  • 仍有重要问题没有解决；
  • 必需证据缺失、冲突、过期或没有绑定到当前版本。

Owner 可以决定

accept 接受

accept_with_conditions 附条件接受

rework 返工

pause 暂停

stop 停止

部署、发布、合规声明和不可逆外部行动需要单独授权。

失败可以提出新规则，但不能自己让它生效

一个项目可以产生学习候选。只有经过证据验证并获得 Owner 授权，它才能在其他范围内启用。

candidate / 候选来自失败、纠正或缺失的控制
→
validated / 已验证预注册比较达到规则，并保留证据、反例、负担、边界与到期条件
→
active / 生效获得授权，并有明确适用范围
→
retired / 退役被替代、被证伪、不再安全或不再相关

validated 不等于 active：激活还必须有 Owner authorization reference 和明确 scope。Agent 可以提出和测试经验，但不能自我授权。新项目只检索最相关的 3 到 5 条 active learning。

当前证据边界

GDAC 是一套由作者维护、在 AI 协助下形成的 Harness 架构与 Eval 规则。仓库测试能够说明：在已声明的样例上，相关 schema、校验器和示例控制按照记录运行。

这些材料不能证明外部采用、生产环境效果、独立保证、组织价值、风险降低、成本下降或法律合规。目前的实践观察包含作者主导的私有项目，外部读者无法独立检查；也没有独立第三方复现这套方法。

面向受监管环境或 AI Act 的附加层，只能做证据映射并提示需要回答的问题。它不能判断法律分类、认证合规，也不能替代有责任主体参与的法律与组织复核。
