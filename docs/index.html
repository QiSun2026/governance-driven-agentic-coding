When execution scales faster than oversight

AI agents can do more software work than one person can inspect line by line. The harder risk is losing the control path around the code.

The question is not only whether an Agent writes correct code. It is also: what was authorized, what changed, what evidence supports the result, who can stop the work, and who decides whether it is acceptable?

When those answers live only in a chat history, the work is difficult to resume, review, or hand over. The Harness makes the outcome, authority, record, evaluation, and decision path explicit.

Failures the Harness is designed to block

  • An Agent silently expands scope or permissions.
  • The frozen pass rule changes after results are known.
  • A summary replaces the original evidence.
  • A model grades its own conclusion in the same context.
  • A passing test is treated as Owner acceptance.
Use full

Material or hard to reverse

Freeze Contract and Eval Plan, use separated review, retain a complete Gate Record, and require Owner disposition.

Use light

Reversible but delegated

Use a short Contract, direct acceptance and authority checks, one Candidate Binding, and a compact Gate Record.

Skip

Trivial or read-only

Use the repository's normal issue, tests, review, and branch rules. GDAC should not manufacture ceremony.

Where it fits in a normal Git workflow

Issue or Contract → checked-in Eval Plan → commit SHA → CI or eval evidence → Gate Record → maintainer / Owner disposition

One task, end to end

A cleanup command needs a --dry-run option that previews the exact changes without calling any inventoried write API inside the declared candidate-process and fixture boundary.

Frozen task boundary

Outcome
Preview the exact change set while initiating no write through the candidate's inventoried write-capable APIs inside the declared boundary.
Acceptance
The API inventory has no uncovered write path, the trace records zero calls, the preview matches normal execution, and existing behavior passes.
Non-goals
No CLI redesign, dependency change, migration, or publication.
Authority
Builder may edit the command and its tests only.
Budget
Two implementation attempts and one bounded review cycle.
Stop
Unexpected write, missing environment, scope expansion, or unresolved material finding.
  1. Owner freezes the Outcome Contract.The result and evidence requirements cannot move unnoticed after implementation begins.
  2. The Eval Plan is locked before coding.Each claim names its grader, required evidence, pass rule, retry budget, and failure consequence.
  3. The execution core makes the smallest change.The Builder works only in declared files and records the diff, attempts, failures, and tests.
  4. The Candidate Binding is recorded.Evaluation binds to one exact artifact, digest, source revision, and attempt. A change creates a new binding and invalidates affected results.
  5. Verifier and Red Team inspect separate failure paths.Instrumentation covers every inventoried write API; an uncovered path becomes insufficient evidence. Regression and challenge cases cover the preview, interruption, and permission errors.
  6. The Harness validates the Gate Record.Attempts, evidence digests, results, contradictions, findings, and the derived gate stay attached to the same candidate.
  7. The Owner decides.A passed technical gate means ready for a decision, not already accepted or authorized for release.

Evaluation starts before building

An Eval Plan is a frozen claim-to-evidence agreement, not a score added after the result looks good.

claim→ eval→ grader→ evidence→ gate→ decision

Before execution

Contract check

Is the outcome specific, testable, bounded, and frozen?

Failure: block before work
Authority check

Is every write, tool, budget, and external action explicitly permitted?

Failure: stop and escalate

Against the candidate

Build integrity

Is the change minimal and clean under applicable type, lint, security, and environment checks?

Failure: rework or stop
Capability and regression

Does the claimed path work without breaking accepted behavior?

Failure: fail or insufficient evidence

Before the Owner

Challenge and review

Were material assumptions, edge cases, and evidence gaps checked from separated context?

Failure: block unresolved findings
Decision readiness

Does the handoff retain limits, unknowns, residual risk, and every mandatory result?

Result: blocked or ready for Owner

Grader rules

Deterministic first. Use code and rule graders when they directly answer the claim.

Regression is mandatory when accepted behavior can break. A new capability does not excuse an old failure.

Adversarial cases follow material risk. Test coverage matters more than test volume.

Model graders retain configuration and calibration. They are never the sole blocking grader for a material claim.

Missing evidence fails closed. It becomes insufficient_evidence, never an estimated pass.

Owner judgment stays separate. Evals return pass, fail, insufficient_evidence, or not_evaluated. One Harness Gate then returns blocked or ready. Only the Owner records a disposition.

Every responsibility has power and limits

Roles are not job titles. A role exists only when it adds evidence, expertise, a materially different challenge, or a state-changing control.

What each Harness responsibility may and may not do
ResponsibilityMay doMay not do
OwnerFreeze outcome, authority, risk, and acceptance. Review material assumptions and unresolved items. Make final and external decisions.Transfer accountability, ignore unresolved items, or rewrite failed evidence as a pass.
OrchestratorCreate bounded task packets, allocate context and budget, enforce stop rules.Expand scope, permission, budget, or acceptance.
BuilderChange declared objects and produce implementation evidence.Write outside scope, weaken evals, or accept its own work.
VerifierRun frozen acceptance and regression checks on the exact candidate.Modify the candidate or redefine success after seeing it.
Red TeamChallenge assumptions, abuse paths, edge cases, and evidence sufficiency.Claim third-party independence or run unlimited challenge loops.
IntegratorAssemble passed material, findings, and the decision handoff.Suppress blockers, merge failed material, or decide for the Owner.

No responsibility creates its own authority. Every material state change traces to a declared permission and sufficient evidence.

Decisions travel through records, not recollection

Summaries reduce reading effort. They never replace the original contract, candidate, tests, findings, or decision.

  1. Outcome Contractresult, authority, budget, stop rules
  2. Eval Planclaims, graders, evidence, pass rules
  3. Attempt Recordactions, failures, usage, unresolved items
  4. Candidate Bindingexact artifact, digest, source revision, attempt
  5. Evidence recordsstable references and digests bound to the candidate
  6. Gate Recordresults, contradictions, findings, blocked or ready
  7. Owner Dispositionconditions, residual risk, next state
  8. Closeoutretained work, prohibited claims, learning candidate

Owner view

Current state, material change, risk, blockers, and decisions required.

Learning view

Failure, correction, proposed preventive check, and evidence needed for re-test.

Public view

Only facts, examples, and limits supported by the accepted evidence record.

A governed system must know when to stop

Stopping is a valid controlled result. Continuing because time has already been spent is not.

The rules require work to remain blocked when

  • required authority, inputs, or acceptance criteria are missing;
  • an action falls outside declared scope;
  • the candidate or Eval Plan changes during evaluation;
  • time, token, attempt, or Agent-depth budget is exhausted;
  • a material finding remains unresolved; or
  • required evidence is missing, conflicting, stale, or unbound.

Deployment, publication, compliance statements, and irreversible external actions require separate authorization.

Failure may propose a rule. It may not authorize one.

A project can create a learning candidate. Only evidence and Owner authorization can make it active elsewhere.

Agents may propose and test a lesson. They may not activate a cross-project rule or silently rewrite the Harness.

A learning candidate records the triggering failure, baseline, proposed rule, observable difference, prospective decision rule, preventive check, burden, counterexamples, boundary, and expiry. Validation never activates it: active status additionally needs an Owner authorization reference and explicit scope. A new project retrieves only the three to five relevant active learnings.

Current evidence boundary

GDAC is an author-maintained Harness architecture and evaluation rule set developed with AI assistance. Repository tests can show that stated schemas, validators, and example controls behave as recorded on the declared cases.

They do not establish external adoption, production effectiveness, independent assurance, organizational value, reduced risk, lower cost, or legal compliance. Current practice observations include private author-run projects that outside readers cannot independently inspect. No independent third party has replicated the method.

A regulated-environment or AI Act overlay may map evidence and flag questions. It does not determine legal classification, certify compliance, or replace accountable legal and organizational review.
